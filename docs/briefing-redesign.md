# 일일 브리핑과 히스토리

## 발행 기준

수집과 브리핑 발행을 분리한다. 시간은 모두 한국 시간(KST)이다.

| 작업 | 시각 | 역할 |
| --- | --- | --- |
| 기사 수집 | 00:00 / 06:00 / 12:00 / 18:00 | 기사 목록 갱신·중복 제거, 기본 LLM 요청 없음 |
| 일일 브리핑 | 매일 06:30 | 전날 06:00 이상~당일 06:00 미만의 24시간 자료를 종합 |
| 정적 배포 | 각 작업의 데이터 커밋 후 | Cloudflare Pages가 HTML·검색 인덱스 생성 |

예를 들어 10월 18일 브리핑은 **10월 17일 06:00~10월 18일 06:00**을 다룬다. 정확히 18일 06:00에 발행한 기사는 다음 날 브리핑에 속한다. 자료의 발행 시각으로 선별하며, 모든 매체의 모든 기사를 수집한다고 보장하지 않는다.

하루 한 편으로 날짜와 주소가 고정된다. 발행 뒤 기사가 추가되거나 모델이 바뀌어도 같은 날짜를 다시 생성하지 않는다. 과거에 발행하지 않은 날짜를 임의로 채우지 않는다. 06:30 전에 수동 실행하면 직전 발행일이 대상이다. 예약 지연과 Pages 빌드로 실제 게시가 늦을 수 있으므로 발행 예정 시각·실제 생성 시각·집계 범위를 구분한다.

## 독자가 보는 화면

홈에서 먼저 하루의 전체 흐름을 읽고, 이슈별 확인된 내용과 해석을 살펴본 뒤 관련 원문으로 이동한다. 개별 기사 추천에 브리핑이라는 이름을 붙이는 구조를 대체했다.

1. **오늘의 브리핑**: 하루의 주제를 담은 짧은 제목 → ‘오늘의 한 줄’ → 설명형 요약 2~3문단 순서다. 제목은 하나의 관점을, 한 줄은 기억할 핵심 의미를 전달한다. 본문에서는 사건·사례·의미나 한계를 완결된 문장으로 읽는다. 문단 아래의 ‘관련 이슈’ 링크로 자세한 내용으로 이동한다. 날짜·집계 범위를 표시하며 날짜별 상세에서는 ‘이날의 한 줄’로 표기한다.
2. **이슈 카드**: 사건 제목, 사실별 요약과 원문 링크, 별도로 표시한 AI 해석. 모델명·제품명·평가명·핵심 개념처럼 중요한 짧은 구절만 누르면 원문이 새 탭에서 열린다. 문장 전체를 밑줄로 덮거나 반복되는 `[1]` 번호를 붙이지 않는다. 링크의 접근성 이름과 툴팁에 출처를 표시하고 하단에는 모든 근거 기사의 원래 제목과 출처를 유지한다.
3. **최근 브리핑 기록**: 홈에서는 오늘을 포함한 최근 7일(KST)의 발행본을 카드로 보여준다. 제목·한 줄·이슈를 훑어보고 상세로 이동한다. 한 줄이 없는 과거 기록은 첫 요약 문단을 보여주며, 발행하지 않은 날짜를 빈 카드로 만들지 않는다. 그 이전 기록은 히스토리에서 모두 찾을 수 있다.
4. **개별 기사 목록**: 홈의 중복 기사 목록을 없애고 뉴스 아카이브로 모았다. 6시간마다 갱신하며 카테고리 탭과 키워드·발행일 범위·출처·지역·AI 요약·북마크 필터를 함께 적용한다. 날짜는 KST 양끝 날짜를 포함하고, 여러 출처를 가진 기사는 해당 출처 중 어느 것으로 검색해도 나타난다. 카드/리스트를 전환해도 조건과 저장 상태를 유지한다.

상단 메뉴 근처에는 한국 시간 기준 오늘 날짜를 표시한다. 브라우저에서 날짜를 갱신하므로 정적 사이트를 새로 배포하지 않아도 자정 이후 날짜와 홈의 최근 7일 범위가 바뀐다. JavaScript가 꺼져 있으면 빌드 시점 날짜·주간 카드와 아카이브 전체 기사를 읽을 수 있다. 필터 조건은 URL에, 북마크와 선호 보기 방식은 해당 브라우저에 저장하며 서버나 LLM 요청이 필요하지 않다.

수집 기사 수나 여러 매체의 보도만으로 ‘인기 순위’, ‘화제성’, ‘독립 검증’을 주장하지 않는다. 현재는 수집한 자료에서 선정한 주요 이슈이며, 실제 커뮤니티 반응 순위는 제공하지 않는다. 서로 다른 사건은 같은 회사나 카테고리라는 이유로 억지로 합치지 않는다.

## 히스토리

- `/briefings/`: 날짜별 목록, 월·키워드 필터, 이슈 제목과 짧은 전체 흐름. 기록 없는 날짜를 만들지 않는다.
- `/briefings/YYYY-MM-DD/`: 당시 요약·출처·집계 범위, 이전/다음 날짜 이동. 날짜당 한 편이므로 별도의 회차 선택 페이지는 없다.
- 개별 기사 아카이브(`/archive/`)와 연결해 ‘그날의 정리’와 ‘수집한 기사’를 각각 찾을 수 있다.
- JavaScript 없이도 날짜 목록·브리핑 내용·원문 링크를 읽을 수 있다. 월·키워드 필터만 JavaScript를 사용한다.
- 공개한 날짜별 본문은 `data/briefings/YYYY-MM.json`에 누적하고 당시 출처 제목과 URL을 함께 보관한다. 현재 기사 제목이 변경되어도 과거 기록은 그대로 남는다.
- 정정은 별도 메모를 추가한다. 요청에 따라 기존 상단 요약의 표현을 편집한 경우 `overview_revision`에 시각·사유를 남기고 화면에 표시한다. 집계 범위와 이슈별 근거, 원래 생성 시각을 유지하며 예약 실행이 과거 기록을 자동으로 다시 쓰지는 않는다. 운영자가 숨긴 기사가 포함된 브리핑은 전체 내용을 비공개 처리하고 기존 주소에 안내를 남긴다. 비공개 내용은 홈·검색·사이트맵에서 제외한다.

## AI 사용과 근거 검사

일일 작업에서 최대 16건의 허용된 자료를 검토하고, 중복 판별·중요도·출처 다양성을 고려해 작성용 최대 8건을 선정한다. 후보 검토와 브리핑 작성에 구조화된 OpenRouter 요청을 최대 2회 사용한다. 최초 후보는 출처별 순환 선택과 최대 4건 제한을 사용한다. 각 자료의 작성용 본문 발췌는 최대 2,400자, 브리핑 생성의 기본 응답 한도는 50,000토큰(`BRIEFING_MAX_TOKENS`)이다. 모든 수집 기사가 포함되는 것은 아니다.

모델은 이슈 1~5개, 사실별 원문 구간 ID와 기사 ID, 링크를 걸 핵심 구절, 전체 흐름, 영향 해석, 제목과 한 줄을 반환한다. 저장 전에 다음을 검사한다.

- 기사 ID와 이슈 참조가 실제 입력에 있는가?
- 근거 인용이 해당 자료 본문 발췌의 연속 문자열로 존재하는가?
- 모든 자료가 고정된 24시간 범위 안에 있는가?
- 요약 구조·길이·한국어 출력이 유효하며 응답이 잘리지 않았는가?
- 새 `daily-brief-v4` 요약이 문단당 2~3개의 완결된 문장으로 구성되는가? 여러 이슈는 2~3문단, 단일 이슈는 1~2문단으로 설명하며 문단별 관련 이슈는 최대 3개다. 제목은 6~60자, 한 줄은 20~120자의 완결된 한 문장으로 작성하며 제목을 그대로 반복하지 않는다. 한 줄이 없는 v1·v2 기록도 계속 읽을 수 있다.
- 링크 구절은 사실 문장에 정확히 한 번 나타나는 2~30자이며 서로 겹치지 않는가? 문장당 1~2개를 권장하며 최대 3개, 전체 링크 길이는 문장의 절반 이하로 제한한다. 해당 사실의 근거 기사 ID만 허용하고 URL은 저장된 출처에서 가져온다. 잘못된 모델 링크 주석만 제거하며 검증된 사실과 하단 원문 목록은 유지한다. 공개 JSON과 빌드에서도 링크 규칙을 검증하고, 링크 주석이 없는 옛 문장은 일반 텍스트로 읽을 수 있다.

문장·문단 검사는 형식 검사이므로 설명의 품질까지 자동으로 판정하지 않는다. 모델은 먼저 사실과 근거를 정리하고 그 범위에서 요약을 작성하며, 기사명 나열·추상적인 결론·근거 없는 추세를 피하도록 지시한다. 원문은 최대 220자 구간과 기사별 ID로 전달하며 모델이 인용문을 새로 쓰지 않고 근거 구간을 선택한다. 서버는 그 구간이 해당 기사에 속하는지 확인한다. 출처 검사는 연결을 확인하는 장치이며 사실의 진실성이나 해석의 정확성을 보장하지 않는다. 화면에도 이를 알리고 원문을 직접 확인할 수 있게 한다. 전문과 근거 인용 문자열은 공개 JSON에 넣지 않는다. TechCrunch·Hacker News·GeekNews처럼 `summarize=false`인 출처는 브리핑 입력에 사용하지 않는다. 접근 허용 호스트·robots·유료 콘텐츠 정책을 유지한다.

6시간 수집에서는 별도 한도 내에서 영어 기사의 한국어 요약을 생성한다. `daily-brief-v9` 일일 브리핑 요청은 주요 이슈에 사용한 기사 중 기존 요약이 없는 기사에 대해 `article_summaries`도 생성한다. 본문에 인용하지 않은 작성 후보의 요약이 반환돼도 자체 원문 근거가 유효하면 아카이브에 저장한다. 필수 요약 누락·중복·입력에 없는 ID·다른 기사의 근거를 거부하며 기존 검증된 요약을 덮어쓰지 않는다. 브리핑과 기사 요약을 같은 저장 트랜잭션에서 발행하고 기사 상태를 `summarized`로 바꾼다. 인용하지 않은 후보를 브리핑 본문이나 출처 목록에 억지로 추가하지 않는다. 요약되지 않은 기사는 원문 링크로 남으며, 별도 수동 `collect --summarize-articles`도 사용할 수 있다. 기사 수만큼 추가 요청하지 않지만 응답 토큰은 증가한다.

## 실행·실패 처리

- 기본 실행기는 GitHub Actions, 대안은 Oracle의 Python + cron이다. Codex는 개발·수동 테스트용이다.
- `collect`는 6시간 단위 성공 기록인 `collection_slot`을 저장한다. `brief`는 06:00 수집 성공 기록이 없으면 LLM 없이 먼저 수집을 복구한다.
- 두 작업은 Actions 동시 실행 그룹과 운영 래퍼의 파일 잠금을 공유한다. 정상 06:00 수집이 늦어지면 브리핑도 기다린다. VM의 잠금 중복 실행은 건너뛰므로 지연 시 수동 확인이 필요하다.
- 같은 발행일이 이미 있으면 네트워크·LLM 호출 전에 종료한다. 요약 가능한 자료가 2건 미만이면 발행하지 않는다.
- 날짜별 유료 요청 시도를 먼저 기록한다. 실패·시간 초과 후 같은 날짜를 자동 재요청하지 않으며 기존 발행본을 유지한다. Actions 캐시 유실 시 실패 요청의 중복 방지는 보장되지 않는다.
- 운영 래퍼가 두 공개 JSON을 검증한 뒤 한 번 커밋한다. 커밋 전 실패는 두 파일을 함께 복원한다. 전송 실패 복구는 [배포 문서](deployment.md)를 따른다.
- 하루 수집 4회 + 브리핑 1회로 월 최대 약 150~155회의 정기 데이터 배포가 생긴다. 일일 LLM 요청은 최대 월 30~31회이며 별도 수동 호출 비용은 추가된다.

## 현재 한계

장기적으로 같은 사건을 연결하는 고정 이슈 ID, 전날 대비 새 사실·반론 추적, 실제 커뮤니티 반응 점수는 아직 없다. 날짜별 기록은 비교의 기초이며 자동으로 사실 변화까지 판정하지 않는다. 뉴스와 브리핑은 월별로 저장하며 이전 URL을 자동 삭제하지 않는다. 전체 정적 빌드와 Pages 파일 수는 장기 운영 중 계속 관찰해야 한다.

검증 결과와 실제 유료 호출 내역은 [verification.md](verification.md)에 기록한다.
